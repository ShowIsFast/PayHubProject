# 压测说明（JMeter）

文件：`unified-order-50.jmx`

目标接口：`POST /openapi/pay/unifiedorder`

---

## 一、为什么是两个场景

压「下单」只有一个场景是不够的，因为你想验证的是两件完全不同的事：

| 场景 | 单号 | 验证什么 | 50 并发会打到哪条代码路径 |
|---|---|---|---|
| A 正常下单 | 每次请求唯一（`A-${__UUID()}`） | 吞吐、延迟、连接池 | 全部走到 `insert` 成功分支 |
| B 并发重复下单 | 50 个线程**共用同一单号** | 幂等是否真的成立 | `先查` 与 `唯一索引冲突` 两条分支 |

99% 的人只做场景 A，然后声称「我的接口是幂等的」——但幂等只有在**同一单号并发**时才会被触发，场景 A 根本测不到。

场景 B 的单号由 `setUp Thread Group` 里的 Groovy 脚本生成（每轮一个全新值），通过 JMeter 属性 `dupOutTradeNo` 传给 50 个线程。这样每跑一次都是「全新单号 + 50 并发」，能稳定复现撞车。

---

## 二、怎么跑

### GUI 方式（推荐第一次用）

```bash
jmeter -t jmeter/unified-order-50.jmx
```

打开后：

1. 点绿色 ▶ 启动
2. 看 **「汇总报告」** 和 **「聚合报告」**
3. 「察看结果树」默认关闭——压测时开着会拖垮 JMeter 自己

### 命令行方式（推荐正式压测）

```bash
# 先确保应用在跑
java -jar target/PayHubProject-0.0.1-SNAPSHOT.jar

# 压测，结果写入 jtl
jmeter -n -t jmeter/unified-order-50.jmx -l result.jtl -j jmeter.log

# 换个端口/机器
jmeter -n -t jmeter/unified-order-50.jmx -Jport=8099 -Jhost=192.168.1.10 -l result.jtl
```

> `-J` 设置的属性对应 jmx 里的 `${__P(port,8080)}`，不需要改文件。

## 三、参数说明

| 参数 | 位置 | 当前值 | 说明 |
|---|---|---|---|
| 并发线程数 | 两个 Thread Group 的 `线程数` | 50 | 想压 200 就直接改 |
| Ramp-up | 场景 A | 5 秒 | 50 个线程用 5 秒爬坡，避免瞬时冲击 |
| Ramp-up | 场景 B | **0 秒** | 必须同时发起，才有撞车效果 |
| 循环次数 | 场景 A | 5 | 总请求 = 50 × 5 = 250 |
| 循环次数 | 场景 B | 1 | 同一单号只该成功一次 |

## 四、实测基线（本机 M 系列 / MySQL 本地 / mock 渠道）

```
summary = 301 in 00:00:05 = 57.3/s   Avg: 100ms   Min: 3ms   Max: 769ms   Err: 0 (0.00%)
```

| 场景 | 样本 | 平均 | 最大 |
|---|---|---|---|
| A 正常下单 | 250 | **17.4 ms** | 655 ms |
| B 并发重复下单 | 50 | **509.9 ms** | 769 ms |

整体百分位：

```
P50 = 6ms    P90 = 433ms    P95 = 597ms    P99 = 767ms
```

> 注意：这个 57.3/s 不是系统容量上限，是「50 线程跑 5 轮、几百个请求」的平均值。
> 真要测容量，用 `-J` 加大线程数，或改成固定时长（`ThreadGroup.scheduler=true`、`duration=300`）。

## 五、最有价值的一个现象：场景 B 慢了 30 倍

场景 A 平均 17ms，场景 B 平均 510ms。为什么？

```
50 个线程同时 insert 同一个 (merchant_no, out_trade_no)
        │
        ├─ 第 1 个线程拿到 InnoDB 插入锁，插入成功
        └─ 其余 49 个线程全部阻塞在这把锁上，等第 1 个 commit
                 │
                 └─ 等到之后拿到 1062 错误（Duplicate entry）
                          └─ 回查已有单 → 返回旧 paymentNo
```

**那 500ms 不是代码慢，是在等锁。** 这个数字直接说明了一件事：
「先查」这层在并发下是不可靠的，最终一定是数据库唯一索引在替它兜底。

## 六、幂等分支的真实分布（本次实测）

跑完 50 个并发重复下单后，应用日志里：

| 分支 | 次数 | 含义 |
|---|---|---|
| `下单幂等命中`（先查直接返回） | **41** | 请求到达时，赢家已经提交完毕 |
| `并发下单冲突`（撞唯一索引） | **8** | 请求到达时，赢家还没提交，被索引拦住 |
| 真正插入成功 | **1** | 只有这一条落库 |
| 合计 | **50** | ✅ 完全对上 |

这正是我们之前讨论的那个结论的实证：

> **如果只写「先查」这一层，这 50 个并发请求里会有 8 个漏过去，产生 8 笔重复支付单。**
> 唯一索引不是「保险」，它是唯一真正起作用的那一层；先查只是帮你省掉 82% 的无效插入。

面试时把这张表讲出来，比背「幂等三板斧」有说服力得多。

## 七、三个可以动手做的调优实验

**实验 1：把连接池压到瓶颈**

`application.yml` 里现在是 `maximum-pool-size: 10`、`connection-timeout: 3000`。
把线程数调到 100、循环 20 轮，观察是否出现：

```
Connection is not available, request timed out after 3000ms
```

出现就说明瓶颈在连接池，不是在 MySQL。再把 pool 调到 30 复测，看 P99 变化。

**实验 2：关掉 URL 里的 `rewriteBatchedStatements`**

W1 只做单条插入，看不出差别；等 W5 做对账批量写入时，这个参数能差 5~10 倍。

**实验 3：把渠道换成真实支付宝**

`payhub.channel.mode=alipay` 后重跑，P99 会从毫秒级跳到几百毫秒——
因为瓶颈从「本地数据库」变成了「网络 RTT + 渠道处理时间」。
这也是为什么支付系统必须做**超时 + 重试 + 幂等**三件套。

## 八、常见坑

| 坑 | 现象 | 处理 |
|---|---|---|
| 应用没起来就开压 | 全是 `Connection refused` | 先确认 `Started PayHubApplication` |
| 开了「察看结果树」 | JMeter 内存爆、客户端成瓶颈 | 压测时保持关闭 |
| 场景 A 不换单号 | 全走幂等分支，测的不是插入 | 保持 `__UUID()` 每次唯一 |
| 断言写成等号匹配 | 响应多了字段就失败 | 用「包含」`"code":"0000"` |
| 重复跑场景 B 用同一个固定单号 | 第二次全走「先查命中」，测不到冲突 | 已用 setUp 脚本每轮生成新单号 |
| 应用不是 8080 端口 | `payUrl` 指向错误地址 | 已改为跟随 `server.port`，或用 `-Jport=` |
