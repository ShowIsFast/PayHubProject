# W1 骨架导读

> 读这份文档的目标：**合上电脑，能白板画出这笔支付的调用链，并说清每一层为什么这么分。**
> 做不到就再读一遍，不要急着写 W2。

---

## 零、先建立一个心智模型

支付系统的本质是：**把「钱」这个外部事实，转换成一串可审计的内部记录。**

所以每一层都在干同一件事的不同侧面：

| 层 | 它回答的问题 | 出错的后果 |
|---|---|---|
| openapi | 谁在调我？参数对吗？ | 被伪造请求刷单 |
| core（支付单） | 这笔支付现在处于什么状态？ | 重复扣款 / 状态错乱 |
| channel（渠道适配） | 外部世界怎么理解这笔交易？ | 渠道字段写错，钱收不到 |
| merchant | 这笔钱算谁的？ | 结算给错商户 |
| common | 单号、签名、返回码 | 全盘皆错 |

**记住一句话：支付系统里，任何"状态"都必须有唯一可信的落点。**
这个项目里，唯一可信的落点是 `payment_order` 表。Redis 再快也只是缓存，MQ 只是搬运工。

## 一、按顺序读，读什么

### 第 1 站：`PaymentOrderService#create`（最重要）

先别看别的，把这一段读三遍。它做了四件事：

```
① 校验商户 + 幂等先查      ← 只读，不加锁
② 落库 CREATED             ← 写，状态是"还没去渠道"
③ 调渠道 prepay            ← 外部 IO，事务外
④ 置 PAYING + payUrl       ← 写
```

**要读懂的三个点：**

**(1) 为什么状态要拆成 CREATED 和 PAYING？**
因为「调渠道」这一步可能失败、可能超时、可能成功但我们没收到响应。
如果一步到位写成 PAYING，失败时你就分不清「渠道没收到」和「渠道收到了但我们挂了」。

**(2) 为什么调渠道不放在事务里？**
渠道超时 10 秒，事务就占着数据库连接 10 秒。并发 100 就是 100 个连接被占死。
这类事故在生产上非常典型。**记住这句：事务里只做数据库操作，绝不做 RPC/HTTP。**

**(3) 这里的幂等到底是几层？**

代码里有三段，但**只有两段是防线，第三段是善后**：

| 代码 | 性质 | 能不能保证正确 |
|---|---|---|
| 先查（select） | **优化**，快路径 | ❌ 有并发窗口：两个线程可能同时查到 null |
| 唯一索引 `uk_merchant_out` | **唯一保证** | ✅ 数据库层原子，没有窗口 |
| catch `DuplicateKeyException` 后回查 | **善后** | ❌ 它没多挡一次并发，只是把 500 翻译成「幂等成功」 |

把这三段叫「三层幂等」是不严谨的——面试官顺着问一句「那第二层和第三层有什么区别」就容易露怯。

真正意义上的「第三层」在方法之外：

- **渠道侧**：支付宝对同一 `out_trade_no` 只承认一笔交易（跨系统幂等）
- **接口层**：`Idempotency-Key` + Redis SETNX，进业务之前就挡住
- **状态层**：支付单终态不可变，重复推进直接返回——但那是**回调幂等**，不是下单幂等

所以准确的说法是：**「下单幂等 = 应用层快路径 + 数据库唯一约束兜底 + 冲突善后」**，
跨系统还要再加渠道和状态机两层。

### 第 2 站：`schema.sql` + `PaymentOrder`

看三个细节：

```sql
CONSTRAINT uk_merchant_out UNIQUE (merchant_no, out_trade_no)   -- 幂等的硬约束
amount BIGINT                                                    -- 分，不是元
ver INT                                                          -- 乐观锁
```

**为什么金额用 BIGINT 存分？**
`0.1 + 0.2 != 0.3` 这个经典问题在钱上是致命的。
整数分 + 只在展示时格式化，是支付系统的通行做法（微信、支付宝内部也是分/厘）。

**为什么唯一索引比代码判断可靠？**
代码判断有并发窗口：两个线程同时 `select` 都返回 null，然后都 `insert`。
唯一索引是数据库层面的原子操作，没有窗口。

> 顺带看下实体类上的注解：`@TableName` / `@TableId` / `@TableField` / `@Version` 不是装饰。
> `@Version` 直接决定上面那条 UPDATE 语句长什么样，而它又必须有
> `MybatisPlusConfig` 里的 `OptimisticLockerInnerInterceptor` 才生效。

### 第 3 站：`ChannelClient` / `ChannelRouter` / `MockChannelClient`

这是**策略模式**最标准的用法，也是 JD 里「对设计模式非常熟悉」的落点。

```java
public interface ChannelClient {
    Channel channel();
    PayResult prepay(PayRequest request);
    ChannelQueryResult query(String outTradeNo);
}
```

**为什么这里适合用策略，而不是 if-else？**
因为「加渠道」是**可预期的、会反复发生的变化**。支付宝 → 微信 → 银联 → 云闪付，
每加一个都改 if-else，就是每次都在改一个已经稳定的方法。

**判断标准**（面试可以这么说）：变化点是否会反复扩展？会 → 策略/工厂；只是分支判断 → if 就好，别过度设计。

### 第 4 站：`PaymentStatus`

```java
case PAYING -> target == SUCCESS || target == CLOSED;
```

一行 switch，挡住了支付系统 80% 的并发问题。
回调重复、消息乱序、补偿任务并发——最终都要经过这个判断。

**思考题**：如果回调先到 `TRADE_SUCCESS` 后到 `WAIT_BUYER_PAY`，会发生什么？
（答案：第二次流转被拒，且被拒绝本身是正确行为，因为状态不能回退。）

### 第 5 站：`SignUtil`

这是全项目唯一「安全相关」的代码，也是最容易被面试追问的。

```
签名串 = 参数按 key 字典序 → k=v 用 & 连接 → 排除 sign 和空值
签名   = SHA256withRSA(签名串, 私钥) → Base64
验签   = 用公钥解签名，比对摘要
```

**两个致命细节：**
1. **签名串里的 value 不做 URL 编码**，编码发生在「提交请求」时。顺序反了永远验不过。
2. 回调验签用的是**支付宝公钥**（渠道的），下单签名用的是**应用私钥**（我们的）。这是两套密钥。

跑一下单元测试，看 `SignUtilTest` 里「篡改金额后验签失败」那个用例——
这就是「为什么支付回调必须验签」的完整答案。

### 第 6 站：`ChannelNotifyController`（反面教材）

这段代码现在还「能跑」，但它有 5 个洞：

```
POST /notify/alipay  {"out_trade_no":"T001","trade_status":"TRADE_SUCCESS"}
```

任何人都能用一行 curl 把订单改成已支付。

**W2 要重写成：**
```
落原始报文 → 验签 → 校验 app_id/金额 → 状态机 CAS → outbox 发事件 → 返回 success
```

现在不理解没关系，但要记住这个顺序。**顺序本身就是设计。**

### 第 7 站：`AlipayChannelClient`

手写而不是用 SDK，是为了让你看到：
`组装参数 → 排序拼串 → 签名 → form 提交 → 解析 JSON`。

真实对接里最容易踩的三个坑：
1. 金额单位（元 vs 分）
2. 私钥格式（PKCS8 vs PKCS1，头尾要不要带）
3. `notify_url` 必须公网可达

## 三、三个动手练习（改完再进 W2）

**练习 1：打开验签开关**
1. 用 `SignUtil.generateKeyPair()` 生成一对密钥（可以写在测试里，把 `toBase64` 结果打印出来）
2. 把公钥填进 `merchant_app.merchant_public_key`
3. `payhub.sign.verify-enabled: true`
4. 用私钥给自己签一个请求，调通；再故意改金额，应该被拒

**练习 2：制造一次并发重复下单**
用 `wrk` 或 `ab` 对 `/openapi/pay/unifiedorder` 打 50 并发、同一个 `outTradeNo`，
观察：是否只产生 1 条记录？日志里出现几次「并发下单冲突」？
（`DuplicateKeyException` 分支就是这个时候触发的）

**练习 3：观察乐观锁真的生效了**
1. 把 `logging.level.com.payhub` 调到 debug，或直接看控制台 SQL
2. 点一次「确认支付」，确认 UPDATE 语句长这样：

```sql
UPDATE payment_order SET status=?, ver=ver+1 ...
 WHERE id=? AND ver=?
```

3. 再对比 `PaymentOrderMapper#casUpdateStatus`（手写版）和 `updateById`（`@Version` 版），
   想想为什么 MyBatis-Plus 的 `@Version` 必须要注册 `OptimisticLockerInnerInterceptor` 才生效——
   **没注册插件时，@Version 就是一个普通字段，一点用都没有。** 这是面试里能立刻区分「用过」和「背过」的细节。

## 五、下一站（W2）

W2 只有一个主题：**把「不可信的回调」变成「可信的状态推进」**。

具体四件事：
1. `payment_callback_log` 建表，先落报文再处理
2. 验签 + 金额比对
3. 状态机 + `ver` 乐观锁 CAS
4. 本地消息表（outbox）+ 定时补偿任务

做完这四件，你就具备了支付岗面试里**最有含金量的一段讲述素材**：
> 「回调的可靠性不是靠 MQ 保证的，是靠验签、幂等、状态机和补偿四层兜底的。」
